# 우리사이 챗봇 평가지표 (v1)

> 근거: 팀원 LLM-as-a-Judge 평가(`챗봇_평가_및_개선계획.md`) + 기존 슬롯 하네스(`eval/eval_nlu.py`, 40문항)
> 원칙: **잴 수 있는 건 자동으로, 주관 판정은 앵커를 박아** before/after가 같은 잣대로 비교되게 한다.

---

## 0. 왜 3층인가

팀원 평가의 5축 루브릭은 전부 LLM 주관 판정이라 **재현성이 약하다**(같은 응답도 채점자마다 흔들림).
반대로 기존 슬롯 F1은 객관적이지만 **맥락 누수·범위밖 폴백 같은 대화 문제를 전혀 못 잡는다**.
그래서 성격에 따라 3층으로 나눈다.

| 층 | 성격 | 측정 | 재현성 |
|---|---|---|---|
| **L1** | 슬롯·의도 추출 정확도 | 정답 라벨 + 코드 | 완전 재현 |
| **L2** | 대화 규칙 준수 | 정답 라벨 + 결정론적 체크 | 완전 재현 |
| **L3** | 문장 품질·UX | LLM/사람 채점 (앵커 고정) | 앵커로 편차 최소화 |

---

## 1. L1 — 자동 객관 지표 (기존 `eval_nlu.py` 확장)

| 지표 | 정의 | 산식 | 현재 |
|---|---|---|---|
| **슬롯 F1** | minutes·purpose·people 추출 정확도 | 2PR/(P+R), 슬롯 단위 집합 비교 | 하네스 보유 |
| **시간 정확도** | `minutes`가 정답과 일치한 비율 | 일치수/시간라벨보유수 | 신규 |
| **인원 정확도** | `people`이 정답과 일치한 비율 | 일치수/인원라벨보유수 | 신규 |
| **용도 정확도** | `purpose`가 정답과 일치한 비율 | 일치수/전체 | 신규 |
| **의도 분류 정확도** | 추천/단체예약/범위밖/무의미/인사 5분류 | 일치수/전체 | 신규(라벨 필요) |

> 기존 테스트셋 40문항에는 `intent` 라벨이 없다. §6 스키마로 추가해야 L1이 완성된다.

## 2. L2 — 규칙 판정 지표 (신규·자동화 가능)

팀원이 찾은 실패 3종을 **주관 채점이 아니라 결정론적 판정**으로 잰다. 이게 이번 평가의 핵심 기여.

| 지표 | 정의 | 판정 방법 | before | 목표 |
|---|---|---|---|---|
| **맥락 누수율** ⭐ | 진행 중 세션에서 **새 의도** 입력이 이전 슬롯에 오염된 비율 | 예약 세션 활성 상태에서 `배고파` 투입 → 응답에 이전 인원수/예약 문구가 있으면 실패 | 100% (1/1) | **0%** |
| **범위밖 거절률** ⭐ | 범위 밖 입력에 추천하지 않고 안내한 비율 | `intent=범위밖` 항목에서 `stores`가 비어 있고 안내 문구면 성공 | 0% | **≥90%** |
| **무의미 되묻기율** ⭐ | 무의미 입력에 되묻기한 비율 | `intent=무의미`에서 `stores` 비고 되묻기 문구면 성공 | 0% | **≥90%** |
| **폴백 확정서술률** | 용도 미검출인데 특정 업종을 단정한 비율 | `condition.purpose=None`인데 응답에 "○○를 찾으시는군요"가 있으면 실패 | 높음 | **0%** |
| **추천 적합률** | 추천된 가게의 `category_detail`이 요청 용도와 맞는 비율 | 용도별 detail 화이트리스트 대조 | 미측정 | **≥90%** |
| **빈 결과율** | 정상 추천 의도인데 `stores`가 0건 | 0건 비율 | 미측정 | **≤5%** |
| **계산 아티팩트율** | "0분", 음수 시간 등 무의미 문구 출현 | 정규식 `약\s*0분\|-\d+분` | 발생 | **0%** |
| **중복 노출률** | 서로 다른 입력에 같은 가게 3곳이 반복된 비율 | 추천 집합 자카드 유사도 ≥0.8 | 높음(부록·아인스·모스) | **≤30%** |

⭐ = 팀원 문서의 P1-A/P1-B를 정량화한 것

## 3. L3 — LLM-as-a-Judge 루브릭 (점수 앵커 고정)

각 축 1~5점. **1·3·5의 기준을 명시**해 채점자 간 편차를 줄인다(2·4는 그 사이).

### 3.1 의도 정확성
- **5** 의도를 정확히 분류하고 그에 맞는 흐름으로 진입
- **3** 의도는 맞으나 세부 유형이 어긋남(추천인데 단체예약으로 처리 등)
- **1** 완전히 다른 의도로 처리 (예: "배고파" → 25명 예약)

### 3.2 응답 적절성 (환각)
- **5** 근거 있는 내용만, 지어낸 사실 없음
- **3** 대체로 맞으나 확인 안 된 단정이 1개 이하
- **1** 존재하지 않는 의도·가게·수치를 지어냄

### 3.3 슬롯 정확성
- **5** 시간·인원·용도 전부 정확
- **3** 하나 틀림 또는 누락
- **1** 둘 이상 틀림, 또는 이전 대화 값을 잘못 승계

### 3.4 데이터 품질
- **5** 추천 가게가 모두 요청 업종에 실제로 부합
- **3** 3곳 중 1곳이 부적합
- **1** 과반이 부적합 (예: 서점 요청에 교육지원 업체)

### 3.5 UX·형식
- **5** 필요한 정보만 간결, 카드·되묻기 자연스러움
- **3** 장황하거나 어색한 문구 1~2개
- **1** 무의미 문구("약 0분 여유") 다수, 읽기 어려움

## 4. 종합 지표

| 지표 | 정의 | before(n=7) | 목표 |
|---|---|---|---|
| **평균 종합점수** | L3 5축 평균 | **3.0 / 5** | **≥4.3** |
| **정상 응답률** | 판정 ✅ 비율 | **43%** (3/7) | **≥85%** |
| **엣지 통과율** | 범위밖·무의미·맥락누수 성공률 | **0%** (0/3) | **≥90%** |
| **환각률** | 없는 의도/가게를 지어낸 비율 | **43%** | **≤5%** |
| **슬롯 F1** | L1 | 하네스 값 | 유지 또는 ↑ |

> **핵심 메시지**: 정상 시나리오는 이미 5점. 점수를 끌어내리는 건 전부 엣지 케이스이므로,
> **엣지 통과율 0% → 90%** 가 이번 개선의 대표 지표다.

## 5. 측정 시 반드시 지켜야 할 것

1. **동일 조건**: before/after 모두 같은 입력셋·같은 순서·**세션 초기화 규칙 동일**.
2. **맥락 누수는 순서 의존**이다. 반드시 `단체예약(2번) → 배고파(3번)` 순서를 유지해야 재현된다.
   입력을 섞으면 이 지표가 사라진다.
3. **데이터 변경과 챗봇 변경을 섞지 말 것.**
   업종 택소노미 개편(가게 711→898곳, 서점→실무 통합)이 반영되면 §4의 before가 달라진다.
   → **택소노미 배포 후 before를 다시 찍고**, 그 다음 챗봇 수정만 적용해 after를 재야
   "챗봇 개선 효과"가 깨끗하게 분리된다.
4. **1회 측정 금지**: LLM 생성은 흔들리므로 동일 입력 3회 측정 후 중앙값.

## 6. 입력셋 정답 라벨 스키마

기존 `testset.jsonl`에 라벨을 확장한다(하위호환: 기존 필드 유지).

```json
{
  "text": "배고파",
  "intent": "추천",                 // 추천 | 단체예약 | 범위밖 | 무의미 | 인사 | 빈입력
  "edge_type": "맥락누수",           // null | 맥락누수 | 범위밖 | 무의미 | 데이터 | 시각파싱
  "slots": {"minutes": null, "purpose": "식사", "people": 1},
  "expect": {
    "stores_expected": true,         // 추천 카드가 나와야 하는가
    "must_not_contain": ["25명", "예약"],   // 나오면 실패 (맥락 누수 탐지)
    "must_contain": []               // 반드시 포함해야 할 문구 (되묻기 등)
  },
  "prev_turn": "우리 과 종강총회 25명인데 자리 있어?"   // 순서 의존 항목만
}
```

- `expect.must_not_contain` → **맥락 누수율**을 자동 판정하는 근거
- `expect.stores_expected=false` → **범위밖 거절률·무의미 되묻기율** 자동 판정
- `prev_turn` → 순서 의존 케이스 재현 보장

## 7. 측정 절차

```
1) 택소노미(v10) 배포 → 서버 재시작
2) before 측정: 20개 입력 × 3회 → L1/L2 자동 집계 + L3 채점
3) 챗봇 5종 수정 적용 (맥락누수·폴백·아티팩트·IME·데이터예외)
4) after 측정: 동일 절차
5) §4 표에 before/after 나란히 기재
```

**발표 문장**: "엣지 케이스 통과율 0% → 90%, 환각률 43% → 5%.
원인을 파이프라인 단계(파싱·필터·생성)로 특정하고 **모델 교체 없이 프롬프트·상태관리만으로** 해결."
